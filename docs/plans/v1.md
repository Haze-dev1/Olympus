# Plan: v1

- **Status:** M1 complete at lab acceptance scope; later milestones not started
- **Date:** 2026-10-19
- **Scope:** [PRD.md](../PRD.md) goals and requirements, [TRD.md](../TRD.md) technical design; progress in [tracker/progress.json](../tracker/progress.json)

Build in this order. Each milestone ends with something that runs on a real server.

M1 now includes catalog/lock resolution, verified SSH deployment, server activation with health checks and confirmation, planning, status, rollback, GC and destroy. The complete CLI cycle runs against a reset Ubuntu lab VM with a pinned nginx test image. Production recipes remain M2 work. See the feature tracker for current evidence and release limits.

## M1: Core on one server

Features: [core-plan-apply](../tracker/features/core-plan-apply.md), [lock-file](../tracker/features/lock-file.md)

Go, single binary ([ADR 0013](../ADR.md#0013-write-olympus-in-go)). Evaluate locally, activate on the server ([ADR 0014](../ADR.md#0014-evaluate-the-stack-locally-into-a-generation-then-activate-it-on-the-server), [0015](../ADR.md#0015-use-one-docker-compose-project-as-the-runtime)).

1. Go module and CLI skeleton; record the build, lint and test commands in `AGENTS.md` and the `olympus-test` skill.
2. `check`: parse and validate `stack.yaml` and `.env` ([spec](../specs/stack-file.md)).
3. `build`: render one hard-coded tool into a generation (Compose file, config files, manifest with hashes). Test that two builds are byte-identical.
4. Lock: fetch the recipe input at a revision, resolve image digests, write `stack.lock` ([ADR 0016](../ADR.md#0016-pin-the-recipe-set-as-a-flake-style-input)).
5. SSH connection with host key checking, OS check, Docker and Compose install, server lock.
6. Activator ([ADR 0017](../ADR.md#0017-activate-on-the-server-and-roll-back-unless-the-cli-confirms)): upload the Linux build with a checksum check; `activate <n>` writes secrets, runs `docker compose up` and health checks, waits for `confirm <n>`, and rolls back on failure or timeout.
7. `apply`: upload store entries and the generation, start the activator, reconnect and confirm.
8. `plan`: diff the built generation against the server's `current` manifest, including drift.
9. `status`, `rollback`, `gc` (with `keep`), `destroy`.
10. JSON Schemas for `stack.yaml` and `recipe.yaml`, used by `check` ([ADR 0018](../ADR.md#0018-build-structured-config-as-data-and-publish-json-schemas)).

Done when: a stack with one tool applies, re-applies with no changes, rolls back after an upgrade, rolls back by itself when the CLI is killed mid-apply, and destroys cleanly.
