## Confirmed findings

### R1 — Medium — Plan writes raw config keys to operator output

- **Evidence and rule** — `internal/plan/plan.go:284–300,323–350,235–242`. Checklist 9 and 19, generic output escaping and A1 when keys contain sensitive material. Parsed map keys become display text verbatim. The existing no-secret-output test checks values.
- **Failure scenario** — An imported recipe config contains a key with a newline or terminal control characters. When the key changes, plan output can present misleading lines or modify the terminal display. A sensitive identifier stored as a key would also end up in the transcript.
- **Fix** — Render key segments with control characters escaped, bound displayed length, and use a file-only diff where keys cannot safely be displayed. Document that semantic key diffs are appropriate only for formats where keys are safe metadata. Add output tests using inert sentinel labels. Generic dependency and secret scanners will miss this data flow.

### R2 — Medium — Catalog limits leave parts of the archive unbounded

- **Evidence and rule** — `internal/catalog/catalog.go:276–281,296–329,358`. Generic input validation and extended checklist E4, CWE-409/CWE-400. The gzip input has a compressed-size limit. Expanded bytes skipped by the tar reader outside the selected subtree and directory records do not use the regular-file budget.
- **Failure scenario** — A catalog archive with a small usable recipe subtree and a much larger compressed payload elsewhere can consume substantially more decompression work than the extraction cap implies. A directory-heavy archive can also exceed the intended entry count while allocating directories in the temporary cache.
- **Fix** — Enforce a rejecting limit on the entire expanded tar stream, count all headers before filtering, and retain the existing per-file and written-byte caps. Test budget exhaustion outside the selected subtree and for directory entries. A source analyzer may flag the decompressor, but the behavioral budget needs a dedicated test.

### R3 — Medium — Plan retains all changed server config bodies in memory

- **Evidence and rule** — `internal/cli/commands.go:107–110`, `internal/plan/plan.go:357–370,408–424`. Generic input validation and checklist 20, CWE-400. Every changed existing file triggers a read and each accepted body remains in a map through comparison. Extension filtering happens later at `internal/plan/plan.go:286–290`.
- **Failure scenario** — A stack update touching many large generated files can exhaust workstation memory or spend the shared CLI deadline on sequential SSH reads before showing a plan. Non-config assets count toward this cost even though they only receive a file-path diff.
- **Fix** — Filter by supported extension before SSH, cap aggregate bytes and file count per plan, and fall back to file-path diffs when the budget is exhausted. Add a fake-runner test for the fallback and read count. This needs behavioral coverage.

### R4 — Low — One failed Oh My Pi config copy can be masked by a later successful copy

- **Evidence and rule** — `recipes/oh-my-pi/recipe.yaml:29–34`, `internal/eval/eval.go:548–550,567–594`. Generic fail-closed rule. With mount-mode skills the init command does not receive the prune prelude. Its separate copy commands let the final command determine exit status.
- **Failure scenario** — If the existing volume has a permission or filesystem error specific to the MCP config destination, the first copy can fail while the update-settings copy succeeds. Compose can then start Oh My Pi with missing or stale MCP configuration.
- **Fix** — Make every managed-file copy failure terminate init. Verify that activation fails if an earlier copy fails and a later destination is writable. A shell linter may assist, but exercise the generated init path.

## Plausible findings

### R5 — Medium — Enabled npm lifecycle scripts can add unpinned build inputs

- **Evidence and rule** — `recipes/claude-code/Dockerfile:15`, `recipes/codex/Dockerfile:14`, `recipes/gemini-cli/Dockerfile:15`. A7 supply-chain intent and ADR 0051. The lockfiles bind package tarballs. The Dockerfiles allow install scripts. The Claude Code and Gemini CLI lockfiles record install scripts.
- **Failure scenario** — If a pinned package's install script fetches mutable artifacts and installs them into the runtime tree, builds from the same lockfile can contain different executable content. Current script network behavior and shipped output remain unverified.
- **Fix** — Audit lifecycle scripts for the pinned versions and supported platforms. Disable them where possible, as Pi does, and pin or checksum any required external artifacts. Dependency auditing complements script inspection.

### R6 — Low — Plan's privileged reads rely on store filesystem integrity

- **Evidence and rule** — `internal/plan/plan.go:401–422`. A3 and generic path validation. Hash and destination checks establish lexical confinement and `--` terminates options. The read itself follows filesystem links and does not check the expected file hash before parsing.
- **Failure scenario** — A damaged or independently modified store entry redirects a planned config read to a different file. Its bytes then travel over privileged SSH and parsed key names may appear in plan output. No supported unprivileged write path into the store was established, and normal rendered files are mounted read-only at `internal/eval/eval.go:513–517`.
- **Fix** — Use a confined server-side regular-file reader for this feature and suppress semantic diffs for entries that cannot be verified. Test a harmless symlink fixture after hardening. Generic scanning will not establish the filesystem preconditions.
