## Ranked findings

Fix order: F1 first, then F2–F4 according to release risk.

### F1 — High: a channel can be accepted without wiring its allow-list (A10, rules drift)

**Remediation status (2026-11-06):** In progress. Missing mappings are rejected by recipe validation and evaluation, with focused tests passing. Live allowed/unlisted sender verification remains outstanding, so fix verification is partial.

**Where:** `internal/recipe/recipe.go:160`; `internal/eval/eval.go:356`, `:380`.

**Failure scenario:** a recipe declares a channel token mapping but omits the `allow` mapping; a stack supplies a nonempty allow-list, passes validation, and starts a bot without receiving the list. If that bot defaults to accepting arbitrary senders, strangers can issue commands under the bot's privileges.

**Fix:** require a supported, nonempty allow-list mapping for every enabled channel and fail closed before rendering; validate the upstream bot's actual semantics.

**Confidence:** confirmed missing mapping; exploitation needs human eyes on the chosen bot's default. **Also caught by:** targeted integration tests, not dependency scanners.

**Fix session prompt:** Fix only F1 in this report: reject channel configurations that cannot deliver and enforce their nonempty allow-list. Add focused tests, avoid unrelated refactoring, and verify supported bots' semantics.

**Verify after:** a recipe with token but no allow mapping must fail before deployment; a valid channel must accept an allowed user and reject an unlisted user on a disposable server.

### F2 — Medium: built-image inputs are not all content pinned (A7, supply chain)

**Where:** `recipes/codex/Dockerfile:12`, `recipes/claude-code/Dockerfile:13`, `recipes/gemini-cli/Dockerfile:13`, `recipes/goose/Dockerfile:12`, `internal/eval/eval.go:751`.

**Failure scenario:** the same locked base and Dockerfile are rebuilt later after a transitive npm dependency or apt package changes or is compromised. The same local image name can represent different bytes, and the tool receives the changed code. Goose's downloaded executable has a checked digest, but apt packages remain mutable.

**Fix:** lock and verify complete build inputs, or distribute and lock immutable built images; record the actual image digest. **Confidence:** confirmed. **Also caught by:** dependency/image scanners may identify vulnerable components, not reproducibility failures.

### F3 — Medium: development clients intentionally bypass release digest matching (A12, rules drift)

**Where:** `internal/deploy/deploy.go:274`, `:327`; `internal/cli/commands.go:43`.

**Failure scenario:** an operator uses a development CLI and a substituted local Linux activator; its self-reported version and locally calculated hash suffice, so it executes as root without a release-build digest. Release clients fail closed when their embedded digest is missing.

**Fix:** require an explicit, conspicuous unsafe development opt-in or a trusted expected digest for every privileged execution; document the trust boundary. **Confidence:** confirmed. **Also caught by:** targeted regression tests.

### F4 — Medium: checksums are not authenticated independently of release assets

**Where:** `.github/workflows/release.yml:25`; `scripts/build-release.sh:83`.

**Failure scenario:** an attacker who can replace release assets replaces both an archive and `SHA256SUMS`; checksum verification alone accepts the substituted archive. **Fix:** publish verifiable build provenance for each archive and checksum manifest and document identity verification. **Confidence:** confirmed. **Also caught by:** supply-chain policy tooling.
